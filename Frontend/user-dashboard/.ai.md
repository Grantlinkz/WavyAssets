## Non-Negotiable Invariants

1. Never implement or alter features outside defined specifications without explicit approval.
2. Never commit secrets, bypass authentication/authorization, or disable security boundaries.
3. **Documentation Updates**: Docs must be updated after every phase or step — keep context files, progress tracking, and code in strict lockstep before declaring work complete.
4. **Error Handling**: Error handling must be implemented as comprehensively as possible or directed to global error handling/boundaries while strictly ensuring security (no leaking internal stack traces, secrets, or database schemas).
5. **Secure Error Handling**: Client responses must never leak stack traces, internal errors, or infrastructure details. Handle exceptions or route to global handlers securely.
6. **Secure Logging**: All emitted logs must redact PII, authorization tokens, secrets, and private credentials.
7. **Testing**: Unit and Integration tests must be updated after every phase or step, arranged strictly in dedicated directories (`Tests/UnitTest/<test-name>` and `Tests/IntegrationTest/<test-name>`).
8. Invariants documented in `architecture.md` and `security.md` must never be violated.

## Human-in-the-Loop Rules

- Always propose an implementation plan or prompt in `prompts/<sprint-name>-<unit-name>.md` and obtain user approval before writing code.
- Stop and prompt for human review whenever encountering ambiguity, architectural pivots, or destructive actions.
- Provide clear verification steps and proof of correctness after completing any unit of work.

---

## Git Commit Standards

- **Git Commit Frequency**: Commit code as you build. Every working session or phase must contain **at least two git commits**.
- **Conventional Commit Patterns**: All git commit messages must strictly adhere to conventional prefixes:
  - `feat:` for new features
  - `fix:` for bug fixes
  - `refactor:` for code refactoring
  - `docs:` for documentation updates
  - `tests:` for tests addition and modification
  - `chore:` for maintenance tasks and environment setup

---

## Pre-Commit Rules

Before committing code, submitting changes, or marking a task complete:

1. Run and pass all static analysis checks (e.g. linter, strict TypeScript typechecks).
2. Ensure the project build succeeds without errors or warnings.
3. Ensure Unit and Integration tests are updated and passing in `Tests/UnitTest/<test-name>` and `Tests/IntegrationTest/<test-name>`.
4. **Error Handling & Logging**: Verify that all new pathways have comprehensive error handling and secure, redacted logging.
5. Update docs and `.ai/progress-tracker.md` with completed items, session notes, and architectural updates after every phase or step.
